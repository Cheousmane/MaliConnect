## 1. Synthèse

MaliConnect est une application déjà riche et globalement bien structurée : routes séparées par domaine, policies nombreuses, transactions sur les opérations sensibles, journal d'audit, tests Feature étendus, TypeScript propre et dépendances sans vulnérabilité connue.

L'état réel n'est cependant **pas celui annoncé par la documentation**. Les vérifications du 17 novembre donnent :

- **8 tests en échec lors de l'audit** sur 262 (254 réussis, 1084 assertions), tous causés par un même défaut de notification ; après correctifs, la suite compte **275 tests réussis, 0 échec et 1192 assertions** ;
- **48 erreurs ESLint**, **36 fichiers Prettier** et **6 fichiers Pint** non conformes lors de l'audit, tous corrigés depuis ;
- un workflow CI SQLite qui ne pouvait pas démarrer, corrigé par un `.env.example` cohérent et des variables d'environnement explicites ;
- deux parcours critiques cassés : l'inscription professionnelle/entreprise et toutes les notifications applicatives, corrigés depuis (voir section 0) ;
- une faille de cloisonnement entre entreprises sur la gestion des collaborateurs, corrigée depuis (voir section 0) ;
- des suspensions de compte et d'entreprise sans effet sur la visibilité publique, corrigées depuis (voir section 0).

**Verdict : l'application n'était pas prête pour une mise en production en l'état lors de l'audit.** Les trois constats critiques et les quatre constats élevés ont depuis été corrigés et couverts par des tests ; les constats moyens restent à traiter avant une exposition publique durable.

## 3. Constats critiques

### C1 — Toutes les notifications applicatives échouent

**Impact** : toute action qui déclenche une notification renvoie une erreur 500 : nouvelle demande de devis, nouveau devis, acceptation de devis, nouvel avis, limite de formule atteinte, confirmation/annulation de réservation. Le centre de notifications est inutilisable. Le défaut existe aussi en production, pas seulement en test.

**Preuves**

- `app/Notifications/ApplicationNotification.php:20` :

```php
abstract class ApplicationNotification extends Notification implements ShouldQueue
```

La classe implémente `ShouldQueue`, mais n'utilise pas le trait `Illuminate\Bus\Queueable` et ne définit ni `$connection`, ni `$queue`, ni `$delay`.

- Laravel lit ces propriétés dès qu'une notification est mise en file, même avec la connexion `sync` :

```php
// vendor/laravel/framework/src/Illuminate/Notifications/NotificationSender.php:234
$connection = $notification->connection;
```

- Les 8 tests cités échouent tous sur cette ligne.
- Les tests qui passent utilisent `Notification::fake()`, ce qui court-circuite l'envoi réel.

**Recommandation**

Ajouter le trait `Queueable` au socle :

```php
use Illuminate\Bus\Queueable;

abstract class ApplicationNotification extends Notification implements ShouldQueue
{
    use Queueable;
    // ...
}
```

Puis ajouter au moins un test qui envoie réellement une notification sans `Notification::fake()` (ou qui vérifie `Queue::assertPushed`), afin d'éviter une nouvelle régression.

**Effort** : quelques minutes.

**Correctif appliqué** : `use Queueable;` ajouté au socle, ce qui fournit `$connection`, `$queue` et `$delay`. Les notifications d'abonnement pointaient aussi vers la route inexistante `pro.plans.index` ; elles utilisent désormais `pro.subscription.plans`. `PlanLimitReachedNotification` ne sérialise plus le modèle `Plan` mais son nom, afin que le plan de secours non persisté reste compatible avec la file. Tests : `NotificationTest` (12), `ServiceRequestTest` (17), `ReviewTest` (16), `PricingSheetTest` (23), dont un test de limite atteinte sans `Notification::fake()`.

### C2 — L'inscription professionnelle et entreprise renvoie une erreur fatale

**Impact** : depuis la page d'accueil, les boutons « Créer mon espace pro » des formules PRO et BUSINESS appellent `/register?plan=pro` ou `?plan=business`. La soumission du formulaire provoque une erreur fatale PHP `Class "App\Http\Controllers\Auth\PermissionCatalogue" not found`. Le compte est créé en base avant l'erreur, mais l'utilisateur n'est ni connecté ni redirigé : il reste bloqué, et une nouvelle tentative sur le même e-mail échoue pour doublon.

**Preuves**

- `app/Http/Controllers/Auth/RegisteredUserController.php:60` :

```php
IdentityProvisioner::ensureRole('professional', PermissionCatalogue::forRole('professional'));
```

Aucun `use App\Support\Identity\PermissionCatalogue;` n'est présent. PHP résout donc le nom dans le namespace courant `App\Http\Controllers\Auth`, où la classe n'existe pas.

- Le formulaire envoie bien `plan` : `resources/js/pages/auth/Register.vue:21`.
- Les liens de la page d'accueil passent `plan.code` : `resources/js/pages/Welcome.vue:869`.
- Aucun test d'inscription ne couvre `plan=pro` ou `plan=business` : `tests/Feature/Auth/RegistrationTest.php` ne teste que l'inscription sans plan.

**Second problème, après correction de l'import** : un compte `plan=business` reçoit le rôle `professional`, qui ne possède pas `businesses.create` (`app/Support/Identity/PermissionCatalogue.php:404-434`). Il ne peut donc pas créer d'entreprise. De plus, la redirection va vers `pro.profiles.create`, pas vers la création d'entreprise (`RegisteredUserController.php:74-77`). Le parcours BUSINESS reste incohérent même une fois l'erreur fatale corrigée.

**Recommandation**

1. Ajouter l'import `use App\Support\Identity\PermissionCatalogue;`.
2. Choisir le rôle selon le plan :
   - `pro` → `professional` ;
   - `business` → `company-manager` (qui possède `businesses.create` et les permissions de gestion d'entreprise).
3. Rediriger un compte BUSINESS vers `pro.businesses.create` (ou vers un écran de choix profil/entreprise), et un compte PRO vers `pro.profiles.create`.
4. Envelopper la création du compte et l'attribution du rôle dans une transaction, pour éviter les comptes orphelins.
5. Ajouter deux tests Feature : inscription `plan=pro` et `plan=business`, avec vérification du rôle, de la redirection et de l'absence d'erreur 500.

**Effort** : 30 à 60 minutes avec les tests.

**Correctif appliqué** : import de `PermissionCatalogue`, mapping `pro` → `professional` et `business` → `company-manager`, création du compte et attribution du rôle dans une transaction, redirection BUSINESS vers `pro.businesses.create`. Tests ajoutés dans `RegistrationTest` (11 tests), dont un par plan avec vérification du rôle, des permissions et de la redirection.

### C3 — Un gestionnaire d'entreprise peut modifier ou supprimer les collaborateurs d'une autre entreprise

**Impact** : faille de cloisonnement (IDOR) entre entreprises. Un responsable de l'entreprise A peut changer le rôle d'un collaborateur de l'entreprise B, ou le supprimer, en passant l'identifiant de ce collaborateur dans l'URL de son entreprise. Il peut notamment promouvoir un compte en `owner` dans B ou supprimer le dernier responsable de B.

**Preuves**

Routes (`routes/pro.php:76-77`) :

```php
Route::patch('businesses/{business}/members/{member}', ...);
Route::delete('businesses/{business}/members/{member}', ...);
```

Contrôleur (`app/Http/Controllers/Pro/BusinessMemberController.php:83-128`) : `update()` et `destroy()` autorisent uniquement `manageMembers` sur `$business`, puis manipulent `$member` sans vérifier que `$member->business_id === $business->id`. La liaison implicite Laravel résout `{member}` globalement, pas dans le périmètre de `{business}`. Aucun `Route::scopeBindings()` n'est utilisé.

**Recommandation**

Ajouter dans `update()` et `destroy()`, avant toute modification :

```php
abort_unless((int) $member->business_id === (int) $business->id, 404);
```

Ajouter deux tests de non-régression : un responsable de A ne peut ni modifier ni supprimer un membre de B (réponse 404), et le membre de B reste inchangé.

**Effort** : 15 à 30 minutes.

**Correctif appliqué** : contrôle d'appartenance `abort_unless((int) $member->business_id === (int) $business->id, 404)` dans `update()` et `destroy()`. Tests ajoutés dans `BusinessTest` (14 tests), dont deux attaques inter-entreprises vérifiant le 404 et l'absence de modification.

## 4. Constats élevés

### H1 — Les suspensions de compte et d'entreprise ne sont pas propagées aux profils publics

**Impact** : un compte suspendu ou une entreprise suspendue conserve ses profils professionnels visibles publiquement, éligibles à la recherche et à de nouvelles demandes de devis. La suspension administrative est donc largement cosmétique : elle bloque la connexion, mais pas l'activité visible ni la réception de demandes.

**Preuves**

- `app/Http/Controllers/Admin/UserController.php:106-131` modifie uniquement `users.status`.
- `app/Http/Controllers/Admin/BusinessController.php:146-148` modifie uniquement `businesses.status`.
- La visibilité publique d'un profil ne regarde que le profil : `app/Models/ProviderProfile.php:244-247` (`isVerified() && is_active`) et `:337-339` (`scopePubliclyVisible`).
- `Public\ProfessionalController@show` ne contrôle que `isPubliclyVisible()` (`app/Http/Controllers/Public/ProfessionalController.php:26`).
- La liste des entreprises disponibles pour créer un profil filtre le statut du membre, pas celui de l'entreprise (`app/Http/Controllers/Pro/ProviderProfileController.php:631-645`).
- Les policies d'entreprise ne vérifient pas `BusinessStatus` (`app/Policies/BusinessPolicy.php:101-104`).

**Recommandation**

- Décider et documenter la règle : une suspension de compte ou d'entreprise doit-elle masquer les profils, ou seulement bloquer la gestion ?
- Dans le cas le plus sûr, propager la suspension aux profils (`is_active = false`) ou inclure le statut du propriétaire et de l'entreprise dans `scopePubliclyVisible()` / `isPubliclyVisible()`.
- Ajouter des tests : profil d'un compte suspendu invisible, profil d'une entreprise suspendue invisible, demande de devis refusée vers ces profils.

**Effort** : 1 à 2 heures selon la règle retenue.

**Correctif appliqué** : `isPubliclyVisible()` et `scopePubliclyVisible()` exigent un profil vérifié et actif, un compte propriétaire `active` et, le cas échéant, une entreprise `verified`. `isManagedBy()` et `BusinessPolicy` bloquent la gestion d'une entreprise suspendue ; la liste des entreprises disponibles pour créer un profil ne propose plus que les entreprises vérifiées. La suspension est donc immédiatement effective sans modifier les profils. Tests : `PublicProfileTest` (profil d'un compte suspendu, profil d'une entreprise suspendue), `SearchTest` (exclusion d'un compte suspendu), `ServiceRequestTest` (demande refusée vers un compte ou une entreprise suspendue).

### H2 — Les pièces jointes des demandes de devis sont stockées sur le disque public

**Impact** : les photos et documents joints à une demande (qui peuvent contenir des pièces d'identité, des devis, des adresses, des informations commerciales) sont accessibles sans authentification via une URL directe. Le nom de fichier est aléatoire, mais toute URL partagée, copiée dans un historique ou indexée reste accessible. Aucune policy n'intervient.

**Preuves**

- `app/Http/Controllers/Requests/ServiceRequestController.php:217-228` :

```php
$path = $file->store('service-requests/'.$serviceRequest->id, 'public');
// ...
'disk' => 'public',
```

- `app/Models/ServiceRequestAttachment.php:34` : `Storage::disk($this->disk)->url($this->path)`.
- Le contrôleur expose directement cette URL : `ServiceRequestController.php:305-310`.
- Aucune route de téléchargement authentifiée n'existe pour ces pièces jointes.

**Recommandation**

- Stocker les pièces jointes sur le disque `local` (privé).
- Ajouter une route de téléchargement protégée par `ServiceRequestPolicy@view` (ou une policy dédiée), qui vérifie l'appartenance de la pièce jointe à la demande.
- Pour l'affichage des images, utiliser une route contrôleur ou des URLs temporaires signées.
- Prévoir une migration des fichiers existants et un test où un autre utilisateur reçoit 403/404.

**Effort** : 2 à 3 heures avec la migration.

**Correctif appliqué** : les nouvelles pièces jointes sont stockées sur le disque privé `local`. `ServiceRequestAttachment::getUrlAttribute()` pointe désormais vers la route nommée `requests.attachments.download`, qui autorise via `ServiceRequestPolicy@view`, vérifie que la pièce jointe appartient bien à la demande puis sert le fichier. Un repli sur le disque `public` permet de télécharger les fichiers historiques sans les exposer directement. Tests : propriétaire autorisé, autre client 403, pièce jointe d'une autre demande 404.

### H3 — `.env.example` est incohérent et casse le job CI SQLite

**Impact** : l'onboarding d'un nouveau développeur et la CI ne peuvent pas démarrer proprement. Le workflow `tests` copie `.env.example` puis lance `php artisan migrate:fresh --seed --force` ; comme le fichier déclare MySQL sans service MySQL dans le job SQLite, la migration échoue. Plusieurs variables de sécurité sont ignorées silencieusement.

**Preuves**

- `.env.example:51` : `DB_CONNECTION=mysql`, alors que le job `sqlite` de `.github/workflows/tests.yml` n'a aucun service MySQL et lance `migrate:fresh --seed` après `cp .env.example .env` (`tests.yml:41-48`).
- Variables de session incorrectes : `.env.example:115-119` utilise `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_HTTPONLY`, `SESSION_COOKIE_SAMESITE`, alors que `config/session.php` attend `SESSION_SECURE_COOKIE` (`:172`), `SESSION_HTTP_ONLY` (`:185`) et `SESSION_SAME_SITE` (`:202`).
- `.env.example:107` utilise `CACHE_DRIVER`, alors que `config/cache.php:18` attend `CACHE_STORE`.
- Niveaux de log invalides : `.env.example:78-83` (`LOG_DEPRECATIONS_LEVEL=sympl`, `LOG_WARNINGS_LEVEL=sympl`, `LOG_NOTICE=sympl`, etc.), alors que `config/logging.php` attend `LOG_LEVEL` et `LOG_DEPRECATIONS_CHANNEL`.
- `COOKIE_DOMAIN` est présenté comme une clé de chiffrement (`.env.example:39-40`), ce n'est pas la bonne variable.
- Manquent notamment `APP_NAME`, `APP_TIMEZONE`, `APP_LOCALE`, `APP_FALLBACK_LOCALE`, `APP_FAKER_LOCALE`, `SESSION_DRIVER`, `VITE_APP_NAME`, `NOTIFICATION_CHANNELS`.
- `APP_ENV=production` et `APP_DEBUG=false` sont les valeurs par défaut d'un fichier destiné au développement local.

**Recommandation**

Réécrire `.env.example` à partir du `.env` local actuel, avec :

- SQLite comme défaut, PostgreSQL commenté ;
- toutes les variables `APP_*`, session, cache, queue, mail, notifications et abonnements ;
- des noms strictement alignés sur les `config/*.php` ;
- un job CI qui ne dépend pas des valeurs de `.env.example` pour la base (variables d'environnement explicites ou `.env.testing`).

**Effort** : 30 minutes.

**Correctif appliqué** : `.env.example` a été réécrit avec SQLite par défaut, PostgreSQL en commentaire et des noms de variables alignés sur `config/*.php` (session, cache, queue, mail, notifications, abonnements). Le job CI SQLite définit explicitement `DB_CONNECTION=sqlite` et `DB_DATABASE=database/database.sqlite`, ce qui le rend indépendant des valeurs du fichier d'exemple.

## 5. Constats moyens

### M1 — Le statut d'un collaborateur d'entreprise n'est pas appliqué aux autorisations

**Impact** : les méthodes `canManageProfiles()` et `canManageMembers()` ne regardent que le rôle, jamais `status`. `BusinessPolicy::membership()` et `ProviderProfile::isManagedBy()` acceptent donc un membre inactif. Le code est incohérent : `ProviderProfile::managers()` filtre bien `status = active` (`ProviderProfile.php:314-319`), et `availableBusinesses()` aussi, mais pas les policies. Aujourd'hui, aucun écran ne permet de passer un membre à `inactive` ; le risque est donc latent, mais l'invariant de sécurité n'est pas garanti.

**Preuves**

- `app/Models/BusinessMember.php:47-58`.
- `app/Policies/BusinessPolicy.php:101-104`.
- `app/Models/ProviderProfile.php:271-286` et `:356-367`.
- `status` est une chaîne libre, sans enum ni cast, dans `business_members` (`database/migrations/2026_11_12_000002_create_business_members_table.php:27`).

**Recommandation**

- Créer un enum `BusinessMemberStatus` (`active`, `inactive`, `suspended`) et le caster sur le modèle.
- Filtrer `status = active` dans `BusinessPolicy::membership()`, `ProviderProfile::isManagedBy()` et `scopeManagedBy()`.
- Centraliser la règle dans un scope `activeMembership()`.
- Ajouter un test : un membre inactif ne peut ni gérer les profils ni les membres.

**Effort** : 1 heure.

### M2 — Les écritures publiques ne sont pas limitées en débit

**Impact** : un compte vérifié peut créer des demandes de devis en masse, envoyer des messages ou des devis sans limite, ce qui spamme les professionnels et remplit la base. L'inscription n'est pas throttle non plus, ce qui permet de créer des comptes professionnels en série. Le login, la recherche et les signalements sont pourtant protégés.

**Preuves**

- `routes/auth.php:17` : `POST /register` sans `throttle`.
- `routes/requests.php:20-27` : création de demande, messages, acceptation/refus de devis sans `throttle`.
- `routes/catalog.php:26` et `:39` : la recherche et les signalements sont protégés (`throttle:60,1`, `throttle:10,1`), ce qui montre que le mécanisme est connu mais pas appliqué partout.
- La création d'une demande déclenche une notification aux gestionnaires du profil (`ServiceRequestController.php:236`), ce qui amplifie l'effet du spam.

**Recommandation**

- `POST /register` : `throttle:6,1` ou `10,1` par IP.
- `POST /demandes` : `throttle:10,1` par utilisateur.
- Messages et devis : limite par demande ou par utilisateur (par exemple 30 messages/minute, 10 devis/minute).
- Ajouter des tests de rate limiting sur au moins l'inscription et la création de demande.

**Effort** : 1 heure.

---

### M3 — L'acceptation d'un devis n'est pas sérialisée

**Impact** : deux acceptations simultanées (double-clic, deux onglets, requêtes concurrentes) peuvent créer deux réservations pour une même demande, ou accepter deux devis différents. Le contrôleur vérifie le statut du devis avant d'appeler le service, mais cette vérification se fait hors transaction et n'est pas refaite sous verrou.

**Preuves**

- `app/Http/Controllers/Requests/ServiceRequestController.php:375-379` : vérification `QuoteStatus::Pending` puis appel du service.
- `app/Services/Requests/BookingScheduler.php:65-91` : `acceptQuote()` ne verrouille ni la demande ni le devis, ne revérifie pas leur statut, et met à jour le devis avant de réserver. Seul le profil est verrouillé, plus tard, dans `book()`.

**Recommandation**

Dans `acceptQuote()`, à l'intérieur de la transaction :

1. verrouiller la demande et le devis (`lockForUpdate`) ;
2. revérifier `quote.status === Pending` et le statut de la demande ;
3. effectuer les mises à jour et la réservation ;
4. ajouter un test de concurrence ou, au minimum, un test qui appelle deux fois l'acceptation et vérifie qu'une seule réservation est créée.

**Effort** : 1 à 2 heures.

---

### M4 — Intégrité des abonnements et des preuves de paiement

**Impact** : plusieurs fragilités sur un flux financier :

1. `SubscribePlanRequest` déclare `proof` nullable, mais `SubscriptionService.php:219` appelle `$proof->store()` sans condition. Le contrôleur bloque le cas « plan sans essai et sans preuve », mais le service reste dangereux pour tout autre appelant.
2. Si un plan avec essai gratuit est souscrit avec une preuve, le fichier est ignoré : le chemin « essai » retourne avant la création du paiement (`SubscriptionService.php:77-112`). La preuve n'est ni enregistrée ni signalée à l'utilisateur.
3. Aucune contrainte d'unicité ne garantit un seul abonnement par propriétaire (`database/migrations/2026_11_16_000001_create_subscriptions_table.php:21`, `2026_11_20_000002_extend_subscriptions_for_saas.php:23`). Deux soumissions concurrentes peuvent créer deux abonnements/paiements en attente.
4. En cas d'échec après `store()`, le fichier peut rester orphelin alors que la transaction SQL est annulée.

**Recommandation**

- Rendre `proof` obligatoire dans le service lorsque le plan n'offre pas d'essai, et tester `$proof !== null` avant `store()`.
- Enregistrer ou supprimer explicitement la preuve dans le chemin « essai » ; ne pas l'ignorer silencieusement.
- Ajouter une contrainte d'unicité adaptée (index partiel sur `provider_profile_id` quand `business_id` est nul, et sur `business_id` sinon) ou une clé de propriétaire dédiée.
- Stocker le fichier avant la transaction et le supprimer en cas d'échec, ou utiliser un mécanisme de nettoyage.
- Ajouter des tests : soumission sans preuve sur plan payant, soumission avec preuve sur plan à essai, double soumission concurrente.

**Effort** : 2 à 3 heures.

---

### M5 — Le provisioning des rôles resynchronise les permissions à chaque inscription

**Impact** : `IdentityProvisioner::ensureRole()` appelle `syncPermissions()` à chaque inscription professionnelle et vide le cache des permissions. Cela peut écraser des permissions personnalisées par un administrateur, provoquer des courses entre inscriptions concurrentes et ajouter un coût inutile sur un endpoint public.

**Preuves**

- `app/Services/Identity/IdentityProvisioner.php:22-35` : `forgetCachedPermissions()`, `firstOrCreate()`, puis `syncPermissions()` inconditionnel.
- Appel depuis `RegisteredUserController.php:60`.

**Recommandation**

- Créer et synchroniser les rôles uniquement dans le seeder (ou lors d'une commande de déploiement).
- À l'inscription, se contenter de `Role::firstOrCreate()` puis `assignRole()`, sans `syncPermissions()`.
- Si le provisioning à chaud reste nécessaire, ne synchroniser que lorsque le rôle vient d'être créé, et ne vider le cache qu'après un vrai changement.

**Effort** : 30 à 60 minutes.

## 6. Constats faibles

### L1 — Documentation obsolète

`docs/architecture.md:154` annonce 262 tests et 1153 assertions « validés », alors que 8 tests échouent et que 1084 assertions sont exécutées. Les sections sur les pièces jointes publiques (`:749`, `:816`) décrivent un choix sans signaler le risque de confidentialité. La documentation doit être mise à jour après correction, pas avant.

### L2 — Pas d'analyse statique PHP

Le projet n'a ni PHPStan/Larastan ni Psalm. Avec 202 fichiers PHP, des policies et des services métier, une analyse statique de niveau 5 à 6 aurait détecté l'import manquant de `PermissionCatalogue` et plusieurs erreurs de type. Ajouter Larastan en CI est recommandé avant la montée en charge.

### L3 — Finitions de configuration et de code

- `package.json` déclare `"license": "ISC"` et un `author` vide, alors que `composer.json` déclare MIT.
- `app/Support/Identity/PermissionCatalogue.php:228-235` contient un docblock orphelin (`Toutes les permissions du catalogue`) suivi d'un second docblock pour `label()` : signe qu'une méthode a été déplacée ou supprimée sans nettoyage.
- `HandleInertiaRequests.php:44-48` partage le modèle `User` complet, les rôles et toutes les permissions à chaque requête authentifiée. Ce n'est pas une faille (les champs sensibles sont masqués), mais c'est un payload inutilement lourd ; un `only()` explicite serait plus sûr et plus léger.
